# M3 — YouTube Adapter Research and Production Boundary

Status: **M3-A Phase A protocol foundation**
Parent research issue: #50
Phase A issue: #140
Policy dependency: #52
Last protocol update: **2026-10-05**

M3 is deliberately split into a provider-feasibility research track and a later
production adapter track. M3-A may observe unstable YouTube delivery behaviour;
M3-B may only adopt the smallest dependency/protocol set justified by retained
M3-A evidence and the licensing/distribution decision in #52.

M3-A is not an acceptance test for YouTube itself. YouTube is an external,
mutable provider and a live provider is never a deterministic oracle.

## 1. Research question

What is the smallest anonymous long-form YouTube VOD delivery path that can
support SpongeTube's existing provider-independent playback/storage model
without embedding unstable provider details into ExtentStore, CoverageIndex,
FetchBroker identity or RecoveryChain semantics?

The research must distinguish:

1. metadata/playability resolution;
2. stream descriptor availability;
3. transport/protocol family (HTTPS, DASH, HLS, SABR);
4. muxed versus split A/V requirements;
5. access requirements (PO token, challenge runtime, login/cookies);
6. bounded media delivery;
7. range/continuation behaviour;
8. descriptor expiry/refresh;
9. cloud-egress/provider blocking;
10. dependency and distribution consequences.

A client profile that works once is not a production selection.

## 2. 2026 external-risk baseline

The following facts are **research inputs**, not SpongeTube contracts.

As of the protocol date, current yt-dlp documentation/source reports that PO
Token enforcement differs by client and request type. WEB can be SABR-only and
requires GVS PO-token support; MWEB commonly requires a GVS PO token; Android
and iOS may require GVS and/or Player tokens; WEB_EMBEDDED is a useful
no-token comparison but only for embeddable content. The same reference source
warns that client behaviour is actively changing.

WEB_SAFARI HLS is retained only as a historical/control lane. Current yt-dlp
maintainer guidance reports YouTube phasing out or locking down those m3u8
formats, so HLS availability must never be frozen as a fallback assumption.

ANDROID_VR is a negative/control lane rather than a recommended path. Current
yt-dlp source notes intermittent/selective PO-token enforcement during 2026 and
that the pinned 1.65.10 profile began returning 403 for all formats in August
2026.

YouTube.js is an MIT-licensed reference implementation for InnerTube/player
behaviour and contains current SABR/PO-token handling. BgUtils is an
MIT-licensed research reference for BotGuard/WebPO semantics; its own
documentation states that it does not bypass BotGuard and still requires a
runtime environment that satisfies the attestation checks.

NewPipeExtractor and Invidious remain useful comparison sources for breakage,
PO-token and SABR trends, but their code is not adopted by this protocol.
Licensing/distribution consequences remain owned by #52.

Reference material:

- https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide
- https://github.com/yt-dlp/yt-dlp/issues/12482
- https://github.com/yt-dlp/yt-dlp/issues/17143

These links document why M3-A measures capabilities instead of assuming them.
They are not runtime dependencies.

## 3. Scope

Phase A builds the research contract only:

- normative probe protocol;
- `m3-a-probe-v1` retained artifact;
- fail-closed schema and semantic validator;
- privacy/redaction invariants;
- negative/falsification tests;
- frozen candidate client lanes and video-case classes.

Phase A does **not**:

- implement a production YouTube extractor;
- generate or persist PO-token values;
- authenticate an account;
- use cookies;
- rotate IPs/proxies;
- implement rate camouflage;
- implement SABR in SpongeTube;
- embed a JS runtime;
- select yt-dlp, YouTube.js, BgUtils, NewPipeExtractor or Invidious as a
  production dependency;
- change any production Android/Core code.

## 4. Initial client lanes

The first decision matrix uses explicit lanes. They are research identities,
not fallback order.

| Lane | Phase-A role | Initial expectation |
| --- | --- | --- |
| `WEB_EMBEDDED` | anonymous/no-token candidate | limited to embeddable videos; must be measured |
| `TV` | anonymous/no-token candidate | detect SABR/DRM; never assume direct HTTPS |
| `ANDROID_VR` | negative/control | historical no-token path with current 403 regression risk |
| `MWEB` | token-gated candidate | measure GVS POT requirement and SABR/direct descriptor availability |
| `WEB` | SABR/token-gated candidate | measure SABR-only state and GVS/Player/Subs requirements |
| `WEB_SAFARI` | historical HLS control | HLS presence is observational only |
| `ANDROID` | deferred token lane | only advance if earlier lanes cannot meet product needs |
| `IOS` | deferred token lane | only advance if earlier lanes cannot meet product needs |

A later protocol revision may add/remove lanes, but a decision run may not
silently change the frozen set.

## 5. Video cases

Video IDs are frozen in the implementation slice before any decision run.
Phase A defines only the semantic classes:

- **V0 — PUBLIC_EMBEDDABLE_LONG_FORM**: public, anonymous, embeddable VOD;
- **V1 — PUBLIC_SPLIT_AV_LONG_FORM**: public anonymous VOD for which at least
  one independent reference reports separate audio/video representations;
- **V2 — PUBLIC_CAPABILITY_CONSTRAINING_NEGATIVE**: public anonymous VOD whose
  embedding/client capability deliberately constrains at least one lane.

Excluded from Phase A:

- age-restricted content;
- private/unlisted-as-secret content;
- members-only content;
- paid content;
- account-only content;
- Shorts;
- Live/DVR.

A case that changes provider status is retained as changed/invalid evidence; it
is not silently replaced inside an existing run.

## 6. Reference-oracle policy

M3-A triangulates provider behaviour; no single extractor is truth.

Initial references:

1. **yt-dlp** — broad client/profile and format-policy reference. Pin exact
   release/commit for each run. Lab/reference only.
2. **YouTube.js** — independent InnerTube/player and SABR-capability reference.
   Pin exact version/commit. Lab/reference only.
3. **BgUtils** — token/challenge-requirement reference only. It must never own
   the media-delivery result in `m3-a-probe-v1`.
4. **NewPipeExtractor/Invidious** — literature/breakage comparison only until
   #52 permits a stronger use.

Disagreement between references is evidence. The producer must retain the
disagreement instead of choosing whichever result makes a lane look viable.

## 7. Retained artifact: m3-a-probe-v1

Every row represents one exact:

`source revision × tool revision × environment × video case × client profile`.

Required retained dimensions include:

- captured UTC timestamp;
- SpongeTube source revision;
- reference tool/version/revision/licence/role;
- GitHub-hosted environment identity;
- authentication/cookie/proxy state (all false in Phase A);
- semantic video case and public video ID;
- exact client profile;
- resolver/playability outcome;
- observed protocol families;
- muxed/split availability;
- DRM presence/absence/unknown;
- Player/GVS/Subs PO-token requirements;
- observed challenge runtime requirement;
- whether a reference tool executed a challenge;
- whether a signed descriptor was observed;
- expiry presence and relative expiry horizon;
- range advertisement;
- bounded delivery result;
- continuation identity;
- explicit limitations.

The artifact never retains the underlying signed URL or token.

## 8. Privacy and redaction

Portable M3-A evidence MUST NOT retain:

- signed `googlevideo`/media URLs;
- any raw YouTube request URL;
- cookies;
- `Authorization`;
- PO-token values;
- Visitor/Data Sync/session identifiers;
- account identifiers;
- raw IP addresses;
- VPN credentials.

The validator scans every retained string and fails on URL/token/credential
fragments in addition to schema-level privacy flags.

A diagnostic artifact requiring any such value must remain ephemeral,
separately access-controlled and outside canonical portable evidence. Phase A
creates no such diagnostic path.

## 9. Bounded live-provider budget

A future probe implementation MUST be deliberately small:

- GitHub-hosted runners only;
- anonymous/no-cookie by default;
- no proxy/IP rotation;
- no automatic account fallback;
- no full media download;
- a selected media probe may request at most **1 MiB**;
- a bot-check/block outcome terminates that lane instead of escalating evasion;
- retries are for clearly classified transient transport/tool failures only,
  never to defeat provider enforcement;
- request counts and retry reasons must be retained where the reference tool
  exposes them.

This limit is a research safety/reproducibility boundary, not a proposed
production fetch size.

## 10. Outcome taxonomy

Resolver outcome:

- `SUCCESS`
- `UNPLAYABLE`
- `BLOCKED`
- `BOT_CHECK`
- `ERROR`

Protocol observations:

- `HTTPS`
- `DASH`
- `HLS`
- `SABR`
- `NONE`

M3-A must keep the following distinctions:

- metadata success vs actual media success;
- direct HTTPS availability vs SABR-only;
- descriptor availability vs GVS authorization;
- provider enforcement vs cloud-egress blocking;
- token requirement vs successful token acquisition;
- muxed compatibility vs split A/V capability;
- DRM presence vs protocol availability.

## 11. Technical viability rules

A lane may be called **BOUNDED_DELIVERY_VIABLE** for a video case only when:

1. resolver outcome is SUCCESS and playability is PLAYABLE;
2. at least one non-DRM delivery option is observed;
3. a bounded media request actually succeeds;
4. the result does not rely on account cookies or IP rotation;
5. retained evidence passes privacy validation.

For product needs that require split A/V, the lane additionally needs
`SPLIT_AVAILABLE` or `BOTH`.

A lane with metadata but no successful bounded delivery is
**METADATA_ONLY**, not viable.

A lane that requires a PO token is **TOKEN_REQUIRED** until a later, explicitly
approved research slice proves a maintainable token path. Phase A does not
reinterpret token requirement as failure and does not implement the token path.

A SABR-only lane is **SABR_REQUIRED**. That result is important even if
SpongeTube has no SABR implementation.

A cloud bot-check is **CLOUD_EGRESS_BLOCKED/UNKNOWN_PRODUCT_VIABILITY**; it is
not evidence that an Android end-user device would fail.

## 12. Descriptor and continuation rules

M3-A must not freeze a hard-coded URL expiry margin.

If a descriptor exposes an expiry, retain only the relative horizon in seconds.
If expiry is absent or unclear, record ABSENT/UNKNOWN and zero horizon.

Range/continuation is measured against bounded media delivery:

- HTTP status and range result;
- whether the same representation/media identity remains usable for a later
  bounded range;
- whether descriptor refresh changes only mutable delivery binding or also
  changes representation identity.

M2's stable-work/mutable-binding model is the hypothesis under test; provider
behaviour may falsify it.

## 13. Decision sequencing

### M3-A0 — protocol foundation

This issue (#140). Merge schema/validator/tests and this document. No live
decision run.

### M3-A1 — reference inventory and frozen case matrix

Pin exact reference versions/commits, freeze V0/V1/V2 IDs, record licences and
expected capabilities. #52 reviews dependency/distribution implications in
parallel.

### M3-A2 — anonymous no-token probe

Run WEB_EMBEDDED, TV and ANDROID_VR/control lanes. Record metadata and bounded
delivery. No token/challenge execution.

### M3-A3 — token/SABR requirement probe

Run WEB/MWEB and only the minimum deferred mobile lanes needed to answer
remaining questions. The first purpose is to classify requirements. Executing
a challenge/token provider requires a separate explicit protocol revision and
must not retain token values.

### M3-A4 — descriptor refresh/range/seek probe

For technically viable lanes, measure descriptor expiry and bounded
continuation/seek semantics without full downloads.

### M3-A5 — decision

Publish compatibility matrix and accepted/rejected/unknown assumptions. Only
then may M3-B select a production adapter shape.

## 14. Exit for M3-A

M3-A is complete only when retained evidence answers, per relevant video case:

- which client lanes resolve anonymously;
- which protocol families are actually available;
- whether delivery is muxed and/or split;
- whether non-DRM bounded media delivery works;
- which token/challenge requirements are observed;
- whether a JS/native challenge runtime is actually necessary;
- descriptor expiry/refresh behaviour;
- bounded range/continuation semantics;
- cloud/provider blocking observations;
- dependency/licence/distribution consequences;
- which assumptions remain unknown.

M3-A completion does not itself authorize release. M3-B remains gated by #52
and by the explicit evidence-backed dependency decision.
