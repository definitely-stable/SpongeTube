# SpongeTube M3 — YouTube Adapter

Status: **M3-A research contract; M3-B blocked on evidence**
Date: **2026-10-11**
Parent roadmap: `.work/ROADMAP.md`
Architecture authority: `.work/ARCHITECTURE.md`
Verification authority: `.work/VERIFICATION.md`
Parent issue: #50 · Contract slice: M3-A0 #140 · Policy dependency: #52

## 1. Goal

M3 determines and then implements the smallest production YouTube VOD adapter
that can coexist with the already-proven Sponge Core without importing mutable
provider mechanics into storage, coverage or fetch ownership.

The milestone is intentionally split:

```text
M3-A0  protocol / evidence foundation
M3-A1  bounded probe implementation
M3-A2  dated evidence matrix
M3-A3  architecture decision
M3-B   production adapter, only if justified
```

M3-A is a live-provider compatibility investigation. It is not a deterministic
performance benchmark and it is not a production extractor implementation.

M0, M1 and M2 are already closed. In particular, M1 proved the persistent
single-owner playback core and M2 proved bounded route/transport/provider
recovery. M3 must consume those boundaries rather than reopening them.

## 2. M3-A0 boundary

M3-A0 adds only research contracts and host-side validation:

- normative M3 contract;
- `m3-a-probe-v1` portable evidence schema;
- fail-closed host validator;
- falsification tests;
- privacy/redaction rules;
- bounded probe budgets;
- reference-oracle policy.

M3-A0 adds:

```text
0 production YouTube adapters
0 production extractors
0 PO-token providers
0 SABR implementations
0 JS/challenge runtimes
0 new Android runtime dependencies
0 provider-specific ExtentStore/CoverageIndex fields
```

A later slice may implement only what this protocol has made observable and
falsifiable.

## 3. Inherited FROZEN boundaries

The following M1/M2 properties remain FROZEN:

- stable media/storage identity is independent of signed URL, route, token,
  provider session and client profile;
- `FetchBroker` remains the single remote media owner;
- provider delivery state is mutable `DeliveryBinding` material, not
  `FetchKey`/`ExtentSpec` identity;
- valid persisted media survives provider rejection, route change and binding
  refresh;
- observation, classification, policy decision and action remain separate;
- retry/recovery remains bounded by the M2 `RecoveryChain`;
- a live provider is never a deterministic acceptance oracle;
- portable evidence contains no provider credentials, tokens, cookies, signed
  URLs or raw network addresses.

M3 does not add provider fields to ExtentStore or CoverageIndex.

## 4. Decision status

### 4.1 FROZEN by M3-A0

- **F-01** M3-A evidence uses explicit three-state observations:
  `PRESENT | ABSENT | UNKNOWN`. Missing evidence is never interpreted as
  `ABSENT`.
- **F-02** token/challenge requirement observations use
  `REQUIRED | NOT_REQUIRED | UNKNOWN | NOT_APPLICABLE`.
- **F-03** every canonical probe is executed on a GitHub-hosted runner and
  records exact source/tool/client/video-case/environment provenance without
  retaining raw egress addressing.
- **F-04** canonical media probing is bounded to at most 8 selected media probes
  and at most 1 MiB read by each media probe.
- **F-05** canonical metadata work is bounded to 32 requests per probe artifact.
- **F-06** full downloads, account credentials, IP rotation/proxy evasion,
  request-rate camouflage and anti-bot bypass implementation are forbidden in
  M3-A.
- **F-07** raw provider content IDs are not required in portable evidence.
  Canonical case identity uses a SHA-256 provider-content fingerprint plus a
  versioned case revision.
- **F-08** reference implementations are evidence oracles only. Their presence
  in M3-A never means production adoption.
- **F-09** a production dependency/adoption decision is impossible until #52
  records its licensing/distribution consequences.
- **F-10** a strong outcome such as `VIABLE_ANONYMOUS`, `SABR_ONLY`,
  `TOKEN_GATED`, `CHALLENGE_GATED` or `DRM_GATED` must be justified by
  compatible recorded observations; the validator fails closed on
  contradictions.

### 4.2 PROVISIONAL until M3-A evidence

- viable client/profile lane;
- GVS or Player PO-token requirement;
- session-context requirement;
- challenge-runtime requirement;
- DASH/HLS/SABR availability;
- split A/V, muxed or interleaved delivery requirement;
- descriptor lifetime/refresh behavior;
- Range/continuation behavior;
- startup/seek/sustained-playback viability;
- production transport/provider component choices;
- production dependency set.

### 4.3 DEFERRED

M3-A does not decide:

- account login;
- age-restricted/private/members-only playback;
- Live/DVR;
- Shorts;
- comments/feed/recommendation features;
- provider-ad handling claims;
- proxy/IP rotation;
- anti-abuse circumvention;
- physical-device performance thresholds;
- M4 Smart Buffer policy.

## 6. Video-case classes

Case definitions are frozen before decision runs.

- **V0** — public, anonymous, embeddable, long-form VOD.
- **V1** — public, anonymous, long-form VOD with split A/V available in at
  least one pinned reference oracle.
- **V2** — public, anonymous, non-embeddable or otherwise
  capability-constraining negative case.

M3-A excludes age-restricted, private, members-only, account-bound and live
content.

Portable evidence records:

```text
caseClass
caseRevision
providerContentIdSha256
```

The raw provider content ID does not need to be retained in portable artifacts.
The probe configuration that resolves the hash may be managed separately from
retained CI evidence.

## 7. `m3-a-probe-v1`

## 8. Observation semantics

Capability fields use:

```text
PRESENT   directly observed by this bounded probe
ABSENT    the protocol performed the required observation and established absence
UNKNOWN   not established
```

`UNKNOWN` is first-class and never coerced to `ABSENT`.

Requirement fields use:

```text
REQUIRED        evidence showed the path cannot proceed without it
NOT_REQUIRED    the observed path proceeded without it
UNKNOWN         not established
NOT_APPLICABLE  the requirement does not apply to the observed path
```

Examples:

- a successful anonymous startup can justify
  `gvsPoToken=NOT_REQUIRED` for that exact lane/case/run;
- a failed request with no token experiment does not by itself prove
  `gvsPoToken=REQUIRED`;
- no HLS URL observed without a complete HLS capability check is `UNKNOWN`,
  not `ABSENT`.

## 9. Bounded provider interaction

Canonical M3-A probe artifacts enforce:

- `metadataRequestLimit = 32`;
- `metadataRequestsUsed <= 32`;
- `mediaProbeByteLimit = 1,048,576`;
- at most 8 media probes;
- `bytesRead <= byteLimit <= 1,048,576` for each media probe;
- `fullDownloadAttempted = false`.

A media probe exists only to establish a bounded capability fact such as
startup bytes, audio/video accessibility, Range, continuation or seek
behavior. M3-A is not a downloader.

If later research needs a different budget, it requires a new versioned
contract rather than silently increasing v1.

## 10. Privacy and redaction

Portable M3-A evidence must never retain:

- any URL in portable M3 evidence (signed or otherwise);
- cookies or `Set-Cookie`;
- `Authorization` or proxy authorization;
- Visitor/session secrets;
- PO-token values;
- access/refresh/ID/bearer tokens;
- passwords/API keys/private keys;
- raw IPv4 or IPv6 addresses;
- raw VPN/Wi-Fi credentials or identifiers.

The host validator recursively scans both structured fields and free-text
limitations. A future schema extension cannot make a secret-class key valid
merely by adding it to JSON Schema.

Redaction occurs before portable artifact persistence. Validation is a second
fail-closed barrier, not the primary redaction mechanism.

## 12. Outcome classifications

`m3-a-probe-v1` permits:

- `VIABLE_ANONYMOUS`;
- `TOKEN_GATED`;
- `CHALLENGE_GATED`;
- `SABR_ONLY`;
- `DRM_GATED`;
- `PROVIDER_REJECTED`;
- `PROVIDER_RATE_LIMITED`;
- `UNSUPPORTED_DELIVERY`;
- `INCONCLUSIVE`.

The validator enforces conservative anchors:

- `VIABLE_ANONYMOUS` requires observed HTTPS startup and no unknown/required
  GVS token, Player token or challenge-runtime dependency for that path;
- `TOKEN_GATED` requires at least one observed required GVS/Player PO token;
- `CHALLENGE_GATED` requires `challengeRuntime=REQUIRED`;
- `SABR_ONLY` requires SABR present and both DASH and HLS observed absent;
- `DRM_GATED` requires DRM present;
- `PROVIDER_REJECTED` requires a retained rejection observation;
- `PROVIDER_RATE_LIMITED` requires a retained throttling observation.

These classifications are scoped to the exact artifact provenance. They are
not global claims about YouTube.

## 13. Guardrails

Every canonical artifact states and validates:

```text
accountCredentialsUsed = false
ipRotationOrProxyEvasionUsed = false
antiBotBypassImplemented = false
requestRateCamouflageUsed = false
fullDownloadAttempted = false
```

If a future product requirement cannot fit those guardrails, it is a separate
policy/security decision and not M3-A.

## 14. Trust and CI model

M3-A uses the same evidence philosophy as M1/M2:

```text
producer
  -> redaction
  -> versioned artifact
  -> JSON-Schema validation
  -> independent semantic/privacy validator
  -> falsification tests
```

Validator:

`scripts/measurement/m3_contracts.py`

Falsification suite:

`scripts/measurement/tests/test_m3_contracts.py`

Repository `Verify` runs the complete `scripts/measurement/tests` discovery, so
M3-A0 contract tests are ordinary required host checks. The committed contract
example is also directly validated by the CLI.

M3-A live-provider results are compatibility observations only. A provider
response cannot become a deterministic release/performance oracle.

## 16. Next slices

### M3-A1 — bounded probe implementation

Status: **Implementation slice #142**

The host-side producer is `scripts/measurement/m3_probe.py`. It executes one
predeclared lane/case at a time and emits only `m3-a-probe-v1`.

Frozen implementation rules:

- yt-dlp `2026.08.19` / release revision
  `594bd50c2c78ac432f81600d309fdc4e0a92d82c` is the initial lab-only
  `REFERENCE_ORACLE`; it is installed only inside the manual probe workflow
  and is not an application dependency;
- every SpongeTube lane maps to one explicit yt-dlp `player_client`;
- the baseline provides no cookies, account credentials, PO-token provider,
  remote component or JavaScript runtime;
- the producer overrides yt-dlp's `YoutubeDL.urlopen` host boundary and refuses
  to send request 33, so the 32-request metadata budget is enforced before the
  network operation rather than checked after the run;
- provider diagnostics, extractor output and signed media URLs stay in memory
  and are reduced to typed observations before persistence;
- direct media observations use only a small fixed probe set and read at most
  64 KiB each (well inside the v1 1 MiB per-probe ceiling);
- Cookie, Authorization and proxy-authorization headers are never forwarded by
  the direct-media probe;
- a successful no-token/no-runtime direct path may prove
  `NOT_REQUIRED` for that exact selected path; token-gated sibling formats do
  not erase a working anonymous path;
- a SABR warning alone proves only `sabr=PRESENT`; it does not manufacture
  `SABR_ONLY` while DASH/HLS absence remains unproven;
- live provider execution is manual `workflow_dispatch` only and never a PR,
  release or deterministic acceptance gate.

Manual workflow:

`.github/workflows/m3-a-probe.yml`

Normal `Verify` executes the deterministic producer falsification suite without
installing yt-dlp or contacting YouTube.

### M3-A2 — evidence matrix

Run predeclared lanes/cases, retain dated artifacts and produce a compatibility
matrix. Repeatability means exact provenance and comparable contracts, not an
assumption that a live provider returns the same result forever.

### M3-A3 — architecture decision

Choose one of:

1. anonymous delivery path is sufficiently viable;
2. token/challenge infrastructure is necessary and acceptable;
3. SABR is necessary and merits an implementation;
4. no acceptable production path is currently justified.

A NO-GO is a valid research result.

### M3-B — production YouTube adapter

Starts only after M3-A3 and #52 justify the boundary and dependency set.
Provider-specific mutable delivery material remains outside Sponge Core
identity/storage contracts.
