# SpongeTube M2 — Network & Provider Resilience

Status: **Implementation contract**
Date: **2026-09-25**
Parent roadmap: `.work/ROADMAP.md`
Architecture authority: `.work/ARCHITECTURE.md`
Verification authority: `.work/VERIFICATION.md`
Parent issue: #74 · Contract slice: M2-A #75

## 1. Goal

M2 makes bad connectivity the normal operating environment without weakening
the M1 core:

```text
observable failure
  -> attributable evidence
  -> conservative interpretation
  -> bounded recovery
  -> same FetchBroker / ExtentStore publication path
```

M1 is closed (`.work/evidence/2026-09-25-m1-canonical-acceptance.md`, 16/16
MUST). M2 builds on the proven fetch/storage/playback core; it does not reopen
M1 identity, storage or fetch-ownership semantics.

This document is the normative M2 contract. M2-A (this contract slice) freezes
invariants, versions evidence identity, assigns ownership and adds falsification
tests. It deliberately does **not** select a transport, a provider
implementation, retry numbers or a runtime API.

A future M2 slice MUST NOT re-decide anything marked FROZEN below. It may refine
PROVISIONAL items inside its owning slice. DEFERRED items are out of M2-A scope
and must not be quietly decided by a runtime PR.

## 2. Starting facts (repository truth at M2-A)

- `FetchBroker` is the single remote media owner; one `SharedFetch` owns one
  bounded, sequential attempt budget (`maxAttemptsPerOwner = 2` in M1).
- `SpongeLoadErrorHandlingPolicy` is a separate, Provisional, bounded Media3
  retry layer (`maxRetries = 3`); each Media3 retry reopens the DataSource and
  can create a fresh `SharedFetch` lifetime.
- `FetchOutcomeKind` already distinguishes `DESCRIPTOR_STALE`, retryable/terminal
  transport, range, integrity and storage outcomes.
- `HttpRangeFetchExecutor` is the M1 deterministic-origin executor, not a
  production transport. `FixtureTransportSession` is an M1 laboratory locator.
- `PlaybackPlan` has no production provider/descriptor/session abstraction yet.
- #50 (M3-A provider feasibility) remains a separate open track.

## 3. Decision status

### 3.1 FROZEN

Changing any of these requires a separate architectural decision (ADR plus
canonical-document update), not a slice-local edit:

- F-01 persisted media identity (`MediaAssetId`, `ExtentId`, `ExtentSpec`,
  `FetchKey`) is independent of route, URL, locator, token and provider session;
- F-02 a route change never invalidates valid persisted coverage;
- F-03 no silent VPN bypass (section 8);
- F-04 Sponge Core / `FetchBroker` remains the only remote media owner;
- F-05 observation ≠ classification ≠ decision ≠ action (section 9);
- F-06 recovery is bounded;
- F-07 a new `SharedFetch`, a Media3 reopen, a route change, a delivery-binding
  refresh or a transport reconnect never grants a fresh recovery budget by
  itself (section 11);
- F-08 mutable delivery state is separate from immutable `FetchKey`/`ExtentSpec`
  (section 12);
- F-09 fault planes are separate and each injected fault has exactly one primary
  owning plane (section 6);
- F-10 every stochastic scenario persists its seed and the seed is part of
  scenario identity (section 7);
- F-11 different clock domains are never directly compared (section 13);
- F-12 evidence never contains provider credentials, tokens, cookies or signed
  URLs (section 15);
- F-13 a live provider is never a deterministic acceptance oracle;
- F-14 bare HTTP 403 is not evidence of a stale delivery binding; HTTP 429 is
  rate limiting (section 10).

## 4. Inherited M1 invariants

These carry over unchanged:

- **M2-I01** `FetchKey` remains stable logical work identity. URL, session,
  token and route are not added to it merely because the delivery method
  changed.
- **M2-I02** `ExtentSpec`, `ExtentId`, `MediaAssetId` and published valid bytes
  do not become invalid because of default-network change, VPN appearance or
  disappearance, provider-locator refresh, transport-backend change or a
  temporary provider rejection.
- **M2-I03** `FetchBroker` remains the single remote media owner.
- **M2-I04** a Media3 reopen does not create an alternative network path.
- **M2-I05** a partial, truncated or mismatched response passes through the same
  M1 publication barrier and never becomes coverage.
- **M2-I06** provider delivery details never enter ExtentStore or CoverageIndex.
- **M2-I07** a runtime-generated conclusion is never the only evidence oracle.

## 6. Fault-plane ownership

| Plane | Owner | Examples |
| --- | --- | --- |
| `DELIVERY` | Sponge Media Lab | pacing, first-body delay, blackout / no-progress window |
| `TRANSPORT` | external M2 transport harness | connect timeout, reset, truncation, slow close |
| `NETWORK` | isolated network harness | RTT, jitter, loss, reorder, duplicate, corruption |
| `PROVIDER` | deterministic provider simulator / adapter policy | 403, 429, expiry, refresh success/failure |
| `ROUTE` | Android route integration | default-network replacement, VPN disappearance |
| `STORAGE` | ExtentStore fault path | ENOSPC, metadata/file I/O |

Rule: **one injected fault has exactly one primary owning plane.** A combined
scenario lists every constituent fault separately, each under its own plane.

A received HTTP status response (403, 429, ...) is a PROVIDER-plane observation:
the transport delivered a response. It is never recorded as a transport/socket
failure.

### 6.1 Scenario families and variants

Scenario family IDs (`N0`–`N11`) stay as human shorthand. They are not identity.
The real identity of an experiment is:

```text
primaryPlane + variant + resolved fault parameters + seed
```

Every resolved M2 scenario carries `scenarioFamily`, `variant` and
`primaryPlane`. Family-to-plane compatibility:

| Family | Permitted primaryPlane | Examples of variant |
| --- | --- | --- |
| N0, N1, N4 | DELIVERY | `CONTROL`, `PACED`, `NO_PROGRESS_120S` |
| N2 | NETWORK | `HIGH_RTT_JITTER` |
| N3 | DELIVERY **or** NETWORK | `BURST_DELIVERY_BLACKOUT` (DELIVERY), `BURST_PACKET_LOSS` (NETWORK) |
| N5 | NETWORK | `BURST_LOSS` (stochastic, seed required) |
| N6 | TRANSPORT **or** ROUTE | `TRANSPORT_RESET` (TRANSPORT), `DEFAULT_ROUTE_REPLACEMENT` (ROUTE) |
| N7 | ROUTE | `VPN_DEFAULT_ROUTE_LOSS` |
| N8, N9, N10 | PROVIDER | `HTTP_403`, `HTTP_429_RETRY_AFTER`, `BINDING_EXPIRY_REFRESH` |
| N11 | STORAGE | `ENOSPC_DURING_RECOVERY` |

N3 and N6 are **not** renamed. `N6 / TRANSPORT_RESET / TRANSPORT` and
`N6 / DEFAULT_ROUTE_REPLACEMENT / ROUTE` are different experiments that happen
to share a family label.

### 6.2 N11 boundary

M2 owns:

- propagation of storage failures into the resilience decision;
- ENOSPC / file or metadata I/O are never classified as provider or network
  failures;
- recovery policy never starts a pointless delivery-binding refresh or
  re-resolve for a storage failure;
- valid coverage stays valid;
- deterministic storage fault injection where it interacts with network
  recovery.

M6 owns production quota, eviction policy, retention, user-facing
storage-pressure handling, background cleanup and large-library behavior.

## 7. Scenario identity and reproducibility

The resolved scenario is `m2-scenario-v1` (section 16). Rules:

- `scenarioHash = SHA-256(canonical resolved scenario bytes)`;
- canonical bytes are UTF-8 JSON with lexicographically sorted object keys,
  no insignificant whitespace, and each plane's fault list ordered by
  `faultId`;
- non-integer numbers are forbidden in resolved scenarios; express fractional
  quantities in integer units (ppm, micro-seconds, bps) so canonical bytes are
  unambiguous;
- a stochastic fault (`stochastic = true`) REQUIRES a non-null integer
  `randomSeed`;
- changing the seed, `primaryPlane`, `variant` or any resolved fault parameter
  changes the hash;
- key ordering does not change the hash;
- a scenario whose primary plane or any fault is ROUTE claims route/VPN
  evidence and MUST set `requiresActualDefaultNetwork = true`; a run of such a
  scenario must traverse Android's selected default network (never
  `adb reverse` or a host-only path);
- a scenario label or family ID alone never identifies an experiment.

## 8. Route contract

### 8.1 Platform sources and API floors

M2-B observes the app's **default** network, never an arbitrary network:

| API | Source |
| --- | --- |
| 24+ | `ConnectivityManager.registerDefaultNetworkCallback()` |
| 23 | context-registered `CONNECTIVITY_ACTION` receiver + `getActiveNetwork()` + `getNetworkCapabilities(activeNetwork)` snapshot |

`registerDefaultNetworkCallback()` exists only from API 24. `CONNECTIVITY_ACTION`
is used **only** on API 23 (Android 6); on API 24+ using it instead of the
default-network callback is forbidden. The API 23 source is a conservative
compatibility source: a receiver only triggers a snapshot, it takes no decision,
and a snapshot whose `activeNetwork` changed during the lookup is discarded
rather than trusted.

Capability API floors (FROZEN):

| Field | Platform source | Floor |
| --- | --- | --- |
| `internet` | `NET_CAPABILITY_INTERNET` | 21 |
| `metered` | inverse `NET_CAPABILITY_NOT_METERED` | 21 |
| `vpn` | inverse `NET_CAPABILITY_NOT_VPN` | 21 |
| `restricted` | inverse `NET_CAPABILITY_NOT_RESTRICTED` | 21 |
| `validated` | `NET_CAPABILITY_VALIDATED` | 23 |
| `suspended` | inverse `NET_CAPABILITY_NOT_SUSPENDED` | 28 |
| `blocked` | `NetworkCallback.onBlockedStatusChanged()` | 29 |

Consequently API 23–27 report `suspended = UNKNOWN` and `blocked = UNKNOWN`;
API 28 reports `suspended` but `blocked = UNKNOWN`; API 29+ may report both.
Below its floor a field is always `UNKNOWN`; the absence of a callback never
produces `FALSE`.

VPN is derived only from `NET_CAPABILITY_NOT_VPN`. Transport types are never
VPN proof: a VPN network may carry VPN plus Wi-Fi/cellular transports.

### 8.2 Route state

The M2-B reducer produces a `DefaultRouteState`:

```text
INITIALIZING                 monitor created, no platform observation yet
UNAVAILABLE                  platform observed no usable default network
AVAILABLE
  routeEpoch
  capabilitiesReceived
  internet validated vpn metered restricted blocked suspended   TRUE | FALSE | UNKNOWN
```

- `INITIALIZING` is the honest start state. It is never equal to `UNAVAILABLE`:
  startup must not manufacture a route-loss event.
- `UNAVAILABLE` does not name a cause. On API 23 `getActiveNetwork() == null`
  may mean "no default network" **or** "default network blocked for this app";
  no evidence claims `NO_DEFAULT` unless the platform proved it.
- `LOST` is an event, not a state; after a loss the state is `UNAVAILABLE`.
- a new `AVAILABLE` epoch starts with `capabilitiesReceived = false` and every
  capability `UNKNOWN`.

Capability fields are tri-state. The tri-state rule is FROZEN: **UNKNOWN is
never interpreted as TRUE or as FALSE** (in particular not as "not VPN"). The
exact Kotlin form is PROVISIONAL (M2-B).

### 8.3 `routeEpoch`

A `routeEpoch` identifies one continuous period during which one specific
`Network` is observed as the app's default network.

```text
INITIALIZING -> AVAILABLE(A)            epoch 1
capability change on A                  epoch 1
AVAILABLE(B)                            epoch 2   (no wait for onLost(A))
late capability event for A             ignored
LOST(B)                                 UNAVAILABLE
AVAILABLE(B) again                      epoch 3
```

- a new epoch starts when a different `Network` becomes the default; it does
  not wait for `onLost()` of the old network, which may still exist physically;
- a network that becomes default again after an `UNAVAILABLE` gap starts a new
  epoch even if Android reuses the same `Network` object;
- capability-only changes on the same `Network` never create an epoch;
- capabilities of an old epoch are never carried into a new one;
- events that name a network other than the current one are stale and never
  mutate state.

### 8.4 Callback ordering

M2-B MUST build state from data delivered by the callbacks themselves
(`onAvailable`, `onCapabilitiesChanged`, `onLinkPropertiesChanged`,
`onBlockedStatusChanged`, `onLost`) through one serialized reducer. It must not
use `onAvailable(network) -> connectivityManager.getNetworkCapabilities(network)`
as the basis of a state transition (race). API ≥ 26 delivers ordered callbacks
after `onAvailable`; on API 24–25 no such order is assumed, and the reducer
behaves identically on every API: `AVAILABLE` with capabilities pending until
capabilities are observed.

### 8.5 VALIDATED is a route observation, not origin reachability

```text
NET_CAPABILITY_VALIDATED  !=  specific media origin reachable
```

- a validated route may still fail to reach the provider media host;
- an unvalidated state is never automatically a provider failure;
- a provider failure is never automatically a route failure;
- `validated = FALSE` alone never pauses external fetching.

### 8.6 Session route guard (VPN continuity)

The process-global route observer knows nothing about playback sessions. VPN
privacy is a **per-session** `SessionRouteGuard`:

```text
UNRESOLVED                 session privacy not yet known -> external fetch PAUSE
SYSTEM_DEFAULT_ALLOWED     session started on a route observed vpn = FALSE
VPN_CONTINUITY_REQUIRED    session started on a route observed vpn = TRUE
```

Resolution happens from the route observed when the session begins external
media activity, or from the first observation with known `vpn` if the session
started while the route was `INITIALIZING`, `UNAVAILABLE`, capabilities-pending
or `vpn = UNKNOWN`. Until then the guard is `UNRESOLVED` and new external
fetches pause.

Sticky rules (FROZEN):

- `VPN_CONTINUITY_REQUIRED` stays until the playback session ends or the user
  explicitly overrides it; another VPN appearing satisfies it but does not
  clear it;
- `SYSTEM_DEFAULT_ALLOWED` never escalates to `VPN_CONTINUITY_REQUIRED` because a
  VPN appeared after the session started: `direct -> VPN -> direct` is not a VPN
  bypass;
- an explicit direct override lifts **only** the VPN-continuity requirement. It
  never lifts `INITIALIZING`, `UNAVAILABLE`, pending capabilities, `blocked`,
  `suspended`, `restricted` or `internet = FALSE`.

`metered` and `validated` are observations only; M2-B never pauses on them.
Metered/data-budget policy belongs to Smart Buffer (M4).

The reference oracle is `scripts/measurement/m2_contracts.py`
(`resolve_session_route_guard`, `evaluate_external_fetch_route`,
`validate_route_privacy_transition`).

## 9. Observation, interpretation, decision, action

```text
OBSERVATION  ->  CLASSIFICATION  ->  POLICY DECISION  ->  ACTION EXECUTION
```

- **Observation** — only an observed fact: socket timeout, connection reset,
  EOF before expected range end, HTTP 403, HTTP 429, `Retry-After` value, route
  epoch changed, validated capability lost, ENOSPC, ...
- **Classification** — conservative semantic interpretation. PROVISIONAL enum
  (M2-C), for example `TRANSIENT_TRANSPORT`, `PROVIDER_RATE_LIMITED`,
  `PROVIDER_REJECTED`, `DELIVERY_BINDING_STALE`, `ROUTE_UNAVAILABLE`,
  `ROUTE_POLICY_BLOCKED`, `RANGE_REJECTED`, `STORAGE_FAILURE`, `UNKNOWN`.
- **Decision** — policy output: `RETRY`, `WAIT`, `WAIT_FOR_ROUTE`,
  `REFRESH_DELIVERY_BINDING`, `RERESOLVE`, `FAIL`.
- **Action** — the operation actually executed: open a new request through
  FetchBroker, wait for a deadline, request a binding refresh, wait for a route,
  terminal completion.

A classifier performs no action. Evidence records the three layers as separate
fields with a shared `failureId`.

FROZEN interpretation anchors:

- storage observations (ENOSPC, file/metadata I/O) classify only as storage
  failure and never trigger `REFRESH_DELIVERY_BINDING` or `RERESOLVE`;
- transport and route observations never classify as provider rejection, rate
  limiting, stale binding or storage failure;
- no decision deletes or invalidates valid persisted coverage.

## 10. HTTP semantic anchors

### 10.1 403

```text
bare HTTP 403  !=  delivery binding stale
```

An observed 403 classifies only as a generic provider rejection until
provider-specific policy has additional evidence. Forbidden:

```text
403 -> delete cache
403 -> automatically refresh URL / delivery binding
403 -> assume expired URL
```

Persisted valid media is never touched. #50/M2-D may later define a
provider-specific signal under which 403 **plus context** is evidence of a stale
binding; M2-A only permits that future classification, it does not choose it.

### 10.2 429

HTTP 429 means rate limiting (RFC 6585). `429 -> PROVIDER_RATE_LIMITED` is a
valid transport-independent classification; the recovery action remains
policy-driven.

`Retry-After` is an advisory server observation. It supports both HTTP forms
(RFC 9110 §10.2.3): `delay-seconds` and `HTTP-date` (IMF-fixdate, with the
obsolete RFC 850 and asctime forms accepted by recipients). Evidence must not
assume a single `retryAfterMs` field. The normalized form is conceptually:

```text
retryAfter
  source        HTTP_HEADER
  rawKind       DELAY_SECONDS | HTTP_DATE | MALFORMED | ABSENT
  delaySeconds? (duration; no clock domain)
  notBeforeUtc? (PROVIDER_WALL_CLOCK domain)
```

An HTTP-date is provider wall-clock time and is never mixed with Android
elapsed realtime. A malformed `Retry-After` is recorded as `MALFORMED`; it never
moves the response to another fault plane or another classification. The exact
artifact is PROVISIONAL (M2-D).

## 11. RecoveryChain and bounded recovery

### 11.1 RecoveryChain

A session is too wide for a budget (one long VOD contains many independent
FetchUnits); a `SharedFetch` is too narrow (a Media3 reopen creates a new owner
lifetime). M2 therefore introduces the conceptual entity **RecoveryChain**: one
logical attempt to satisfy one missing immutable media work item.

```text
Playback needs FetchKey X
  -> RecoveryChain R1
       SharedFetch owner #1: attempt 1, attempt 2
       Media3 reopen
       SharedFetch owner #2
       route change
       delivery binding refresh
       attempt
  -> SUCCESS | TERMINAL_FAILURE | NO_REMAINING_DEMAND | SESSION_TERMINATION
```

`RecoveryChainId` lifecycle:

- starts at the first unsatisfied demand for the immutable work item;
- persists across `SharedFetch` owner replacement, Media3 reopen, retry, route
  pause/resume and delivery-binding refresh;
- ends at exactly one of `SUCCESS`, `TERMINAL_FAILURE`, `NO_REMAINING_DEMAND`,
  `SESSION_TERMINATION`;
- a terminal chain never spends budget again;
- if the immutable `FetchKey`/`ExtentSpec` identity changes, it is a different
  chain, never a continuation.

The runtime representation is owned by M2-C.

### 11.2 RecoveryBudget invariants

FROZEN properties (numbers and dimensions are not):

- the budget is bound to one `RecoveryChainId`;
- the policy has a versioned identity (`policyId`), constant within a chain;
- every spending action produces an explicit charge;
- the ledger is monotonic: `spentAfter >= spentBefore` component-wise; a
  dimension never disappears;
- a charge changes the ledger by exactly the charged amount;
- no internal layer transition resets or changes the ledger by itself; in
  particular a new `SharedFetch`, a Media3 reopen, a `routeEpoch` change, a
  delivery-binding refresh and a transport reconnect do not grant new budget;
- a terminal chain does not continue spending.

PROVISIONAL (M2-C): whether the budget is scalar, a vector or action-specific;
action costs; limits. M2-A does not freeze `PHYSICAL_REQUEST = N`,
`DESCRIPTOR_REFRESH = N` or a mandatory bucket set.

The existing per-owner (`FetchBroker`) and Media3 retry limits remain in place
as inner bounds; RecoveryChain is the outer bound that makes them composable.

## 12. Stable identity versus mutable delivery binding

```text
Stable media identity          Mutable delivery binding
  MediaAssetId           !=      locator
  FetchKey                       token / session
  ExtentSpec                     route-compatible transport state
                                 provider context
```

`DeliveryBindingRevision` (provider-neutral; the name may change after review)
is the version/correlation identity of the mutable delivery material required to
fetch already-known stable media work. It may denote a signed URL set, an HTTP
locator set, a stateful transport session, continuation/session context or a
future provider-specific binding. Core does not know its content. The term
"DescriptorGeneration" is not used as a core term because it is URL/DASH
centric.

Rules:

- refresh/rebind may change only the right-hand side;
- refresh/rebind never silently changes the left-hand side;
- if the provider offers material incompatible with the immutable expected work,
  the outcome is **FAIL CLOSED** or a **higher-level RERESOLVE**; the existing
  `ExtentSpec` is never mutated;
- a successful rebind yields a different `DeliveryBindingRevision` for the same
  stable work.

## 13. Clock domains

| Domain | Source |
| --- | --- |
| `ANDROID_MONOTONIC` | `SystemClock.elapsedRealtimeNanos()` |
| `HOST_MEDIA_LAB_MONOTONIC` | Media Lab monotonic clock (already used by M0/M1) |
| `HOST_FAULT_MONOTONIC` | clocks of host fault tools (transport/network harness) |
| `PROVIDER_WALL_CLOCK` | provider expiry, HTTP-date, provider virtual wall clock |

A correctness proof never computes `androidElapsed - hostElapsed`,
`providerUtc - androidElapsed`, or orders absolute values across domains.
Durations and ordering inside one domain are allowed. Cross-domain joins use
correlation identities only.

## 14. Correlation vocabulary

Existing identities keep their meaning: `sessionId`, `fetchId`,
`attemptCorrelationId`, `transportCorrelationId`.

M2 adds, conceptually:

| Identity | Meaning | Owner |
| --- | --- | --- |
| `recoveryChainId` | one logical recovery of one immutable work item | M2-C |
| `routeEpoch` | one default-network period (section 8.3) | M2-B |
| `failureId` | joins observation, classification, decision and action rows | M2-C |
| `deliveryBindingRevision` | version of mutable delivery material | M2-D |
| `policyId` | versioned identity of a recovery/privacy policy | M2-B/M2-C |

A new ID is not introduced when an existing ID already carries the same
semantics.

## 15. Evidence privacy

Committed or portable raw evidence never contains:

- signed provider URLs or any URL carrying query credentials;
- cookies, `Authorization` values, bearer tokens;
- PO tokens, visitor/session secrets, API keys;
- VPN endpoint credentials;
- raw IP addresses unless a dedicated diagnostic experiment requires them;
- SSID/BSSID.

Correlation uses opaque IDs, or a deterministic hash only when that is safe for
the input class. For secrets even a hash may leak, so the default is: **do not
retain the secret at all.** `scripts/measurement/m2_contracts.py` provides a
fail-closed scanner used by the M2 contract tests; owning slices apply it to
their artifacts.

## 16. Evidence strategy

Lesson from M1: an artifact schema becomes canonical together with its owning
producer and verifier, not several slices earlier. M2-A therefore creates only
the two **cross-slice** contracts:

| Artifact | Purpose |
| --- | --- |
| `m2-scenario-v1` | resolved scenario identity: family, variant, primaryPlane, per-plane faults, seed, actual-route requirement |
| `m2-run-manifest-v1` | per-run identity: commit, fixture, scenario hash, playback mode, media path, opaque versioned transport backend ID, fault-harness and policy identities, device/runtime, clock domains, limitations |

`transport.backendId` is a versioned opaque ID, not a closed enum, because M2
exists to compare transport implementations.

Subsystem evidence is created by its owning slice together with producer,
verifier, deterministic execution path and falsification test:

| Slice | Artifact(s) |
| --- | --- |
| M2-B | `route-events-v1` |
| M2-C | `failure-decision-events-v1`, `recovery-budget-events-v1` |
| M2-D | `delivery-binding-events-v1`, `provider-fault-events-v1` |
| M2-E | `fault-harness-events-v1`, `network-calibration-v1` |

M1 historical schemas are never rewritten to carry M2 semantics; M2 adds new
versioned artifacts.

## 17. Host-side contract verifier

`scripts/measurement/m2_contracts.py` checks only FROZEN contracts. It is a
reference oracle for the contract, not a simulation of production M2:

- `canonicalize_scenario` / `scenario_sha256` — deterministic identity;
- `validate_scenario_semantics` — plane ownership, family/plane compatibility,
  seed requirement, actual-route requirement, no contradictory ownership;
- `validate_run_manifest_semantics` — scenario hash binding, media path for
  route scenarios, harness per faulted plane;
- `resolve_session_route_guard` / `evaluate_external_fetch_route` /
  `validate_route_privacy_transition` — session route guard: a VPN-started
  session never auto-allows a non-VPN route, a direct-started session is not
  escalated by a later VPN, override scope is VPN continuity only;
- `known_true` / `check_route_capability_claim` — `UNKNOWN` never becomes TRUE;
- `check_capability_api_floor` — capability fields below their API floor are
  `UNKNOWN`;
- `validate_persisted_identity_invariance` — route/binding transitions do not
  mutate or remove persisted extent identity;
- `classify_http_contract_case` / `parse_retry_after` — 403/429 anchors;
- `validate_failure_record` — observation/classification/decision separation
  and interpretation anchors;
- `validate_recovery_ledger` — generic RecoveryChain budget lineage;
- `validate_delivery_rebinding` — stable work immutability and fail-closed
  rebinding;
- `check_clock_relation` — no cross-domain comparison;
- `scan_evidence_privacy` — section 15.

`scripts/measurement/tests/test_m2_contracts.py` runs in `Verify` through the
existing host test discovery.

## 18. Acceptance framework

### 18.1 Executable-gate rule

A gate is executable only when its owning slice provides:

1. an evidence producer;
2. an independent verifier where required;
3. a deterministic execution path;
4. a negative/falsification test.

### 18.2 Foundation gates

M2-A defines these seven cross-slice gates. Later slices may **add** IDs;
no artificial reservation of a fixed count.

| ID | Name | Contract |
| --- | --- | --- |
| M2-ACC-01 | Scenario Identity | a resolved stochastic scenario has canonical identity and a persisted seed |
| M2-ACC-02 | Fault Attribution | each injected fault has exactly one primary fault plane |
| M2-ACC-03 | Route Privacy | VPN disappearance never leads to automatic direct-route external fetching |
| M2-ACC-04 | Persisted Media Independence | route or delivery-binding change never invalidates valid persisted media identity |
| M2-ACC-05 | Failure Separation | evidence separately represents observation, classification and recovery decision/action |
| M2-ACC-06 | Bounded Recovery Lineage | one RecoveryChain never receives implicit fresh budget across broker/Media3/route/refresh boundaries |
| M2-ACC-07 | Mutable Binding Independence | a binding can be refreshed without changing stable work identity; incompatible rebinding fails closed |

M2-A establishes the **contract** of these gates and their reference
falsification tests. It does not claim that Android or runtime code passes
M2-ACC-03..07; runtime proof is produced by the owning slices (M2-B..M2-F) and
aggregated in M2-H. M2-ACC-01/02 become executable for runs once an M2 run
producer exists (M2-E); M2-A proves only their definition.

### 18.3 M2-A falsification checklist

The M2-A contract suite fails on each of:

1. N5 stochastic scenario without seed;
2. seed change that does not change the scenario hash;
3. one resolved fault claiming two primary planes;
4. N7-like route proof on a non-default-network path;
5. `UNKNOWN` validated interpreted as TRUE;
6. VPN → direct automatically allowing external fetch;
7. route change mutating persisted media identity;
8. bare 403 automatically declared stale binding;
9. 429 recorded as a generic socket/transport failure;
10. RecoveryChain budget reset after a new `SharedFetch`;
11. reset after a Media3 reopen;
12. reset after a route change;
13. reset after delivery rebinding;
14. mutable delivery binding changing immutable `ExtentSpec`;
15. storage ENOSPC classified as provider rejection;
16. a correctness proof comparing absolute Android and host clocks;
17. schema/evidence containing a raw signed URL, token or credential;
18. a historical M1 artifact contract silently rewritten under M2 semantics.

Route contract correction (M2-B prerequisite) adds:

19. a session that started direct being escalated to VPN-required by a VPN
    that appeared later (`direct -> VPN -> direct` must stay allowed);
20. an explicit direct override lifting `UNAVAILABLE` or `blocked`;
21. `INITIALIZING` treated as `UNAVAILABLE` (or as a route loss);
22. a capability claimed below its API floor (`suspended` < 28, `blocked` < 29);
23. an unresolved session guard (`vpn = UNKNOWN` at session start) allowing
    external fetch.

## 19. Transport and fault tooling (requirements for M2-E/M2-G)

M2-A adds no Toxiproxy/netem dependency.

Transport fault harness: timeout, connection reset, truncation, slow close.
Toxiproxy remains a candidate, not an accepted dependency.

Network fault harness: delay/jitter, loss, corruption, duplication, reordering,
rate, with a persisted seed. `tc/netem` remains a candidate. Requirements:
scoped media path, persisted seed, and an unaffected orchestration/control
path — ADB, Media Lab control, artifact collection and emulator orchestration
must not be impaired together with media traffic.

Transport comparison (M2-G) uses the experiment contract:

```text
same fixture, same scenario, same device state, same playback mode,
same cache/seed state, same ordering protocol — only transport backend differs
```

Synthetic throughput alone cannot select a winner. M2-G weighs playback
resilience, startup, request correctness, reconnect behavior, route
replacement, cancellation, CPU and memory, plus battery/thermal on physical
devices whenever a performance claim is made.

### M2-B — Route Observation & Privacy Policy

First production Android route code, in `:core:engine`
(`io.github.definitelystable.spongetube.core.engine.route`, all `internal`):

```text
API 24+  ConnectivityManager.registerDefaultNetworkCallback
API 23   CONNECTIVITY_ACTION + activeNetwork snapshot
  -> RouteSignal -> Channel(UNLIMITED) -> one reducer coroutine
  -> DefaultRouteState
SessionRouteGuard
  -> ExternalFetchRouteDecision (ALLOW | PAUSE + reason)
```

Kotlin representation (section 8, PROVISIONAL detail owned by M2-B):

- `ObservedBoolean` TRUE | FALSE | UNKNOWN (no nullable Boolean);
- `DefaultRouteState` = `Initializing` | `Unavailable` |
  `Available(routeEpoch, capabilitiesReceived, RouteCapabilities)`;
- `RouteCapabilities` = internet, validated, vpn, metered, restricted,
  blocked, suspended;
- `PlatformRouteRef` (`p1`, `p2`, ...) is process-local; `android.net.Network`
  never leaves the platform adapter;
- `SessionRouteGuard` / `ExternalFetchRouteDecision` with reasons
  `ROUTE_READY`, `EXPLICIT_DIRECT_OVERRIDE`, `INITIALIZING`,
  `NO_USABLE_DEFAULT`, `CAPABILITIES_PENDING`, `SESSION_ROUTE_UNRESOLVED`,
  `VPN_CONTINUITY_REQUIRED`, `NETWORK_BLOCKED`, `NETWORK_SUSPENDED`,
  `NETWORK_RESTRICTED`, `NO_INTERNET_CAPABILITY` (route-policy reasons, not
  M2-C classifications).

Platform rules: callbacks only convert delivered objects into signals (no
ConnectivityManager lookup inside a callback); on API 24+ one `activeNetwork`
lookup after registration resolves INITIALIZING without reading capabilities;
the API 23 snapshot discards a lookup whose `activeNetwork` changed and retries
at most once. `open()` registers exactly once; `shutdown()` marks closed,
unregisters, stops accepting callbacks, closes the channel and awaits the
reducer; a second shutdown is a no-op and a failed open leaves nothing
registered. The library manifest declares `ACCESS_NETWORK_STATE` only; no
location permission and no `FLAG_INCLUDE_LOCATION_INFO`.

`route-events-v1` (`.work/schemas/route-events-v1.schema.json`) records every
reduced signal (`events[]`: sequence, `ANDROID_MONOTONIC` timestamp, source,
signal, disposition, route ref, epoch before/after, observed values, runtime
state after) and, separately, every session policy evaluation
(`policyEvaluations[]`: route-event watermark, epoch, guard before/after,
override, decision, reason). `scripts/measurement/m2_route_oracle.py` replays
the signals with its own state machine, replays the guard through
`m2_contracts.py` and writes `route-verification-summary-v1`. Producers:
`RouteEvidenceHostTest` (scripted API 23/24/28/34/36 sequences, `Verify`) and
`AndroidDefaultRouteMonitorTest` (actual emulator default network; exported on
API 34/36, instrumentation-only on API 23).

Scope boundary: M2-B does not wire the decision into FetchBroker,
PlaybackBridgeRuntime, HttpRangeFetchExecutor or SpongeLoadErrorHandlingPolicy,
and implements no retry, RecoveryChain, VPN harness or network binding. It
proves the policy component of M2-ACC-03 and that the route subsystem has no
mechanism to mutate persisted media (M2-ACC-04 component); the end-to-end
gates remain with M2-F/M2-H:

> M2-B proves route observation, reduction and session privacy-policy
> semantics. It does not prove that a real media fetch is paused during an
> Android VPN/default-route transition. That end-to-end proof belongs to M2-F.

M2-B falsification (host oracle): INITIALIZING reported as UNAVAILABLE; API 23
artifact claiming the default callback; API 27 claiming `suspended`; API 28
claiming `blocked`; new route inheriting old capabilities; same-route capability
change incrementing the epoch; replacement not incrementing it; stale old-route
event mutating state; UNKNOWN VPN treated as direct; VPN-required session
auto-allowing direct; direct-start session escalated by a transient VPN;
override allowing a blocked/unavailable route; runtime decision disagreeing
with the oracle; Network/netId/IP/SSID/BSSID in evidence; out-of-order events;
decreasing `ANDROID_MONOTONIC` time; a complete run without MONITOR_STOPPED.
