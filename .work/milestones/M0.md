# M0 — Reproducible Android & Media Evidence Bootstrap

Status: **Complete**
Parent issue: **#3**
Date: **2026-09-21**

## 1. Purpose

M0 does not implement Sponge Core.

M0 establishes a small, reproducible Android/media laboratory capable of proving or disproving the assumptions that M1–M4 will depend on.

The milestone answers five questions:

1. Can SpongeTube be built reproducibly on a current Android toolchain?
2. Can the same controlled VOD be played through comparable Media3 baseline paths?
3. Can slow/intermittent connectivity be reproduced without depending on live YouTube?
4. Can playback, network and storage outcomes be measured in a machine-readable form?
5. Can CI reject correctness regressions quickly without pretending emulator numbers are real-device performance evidence?

M0 succeeds when later claims such as "Sponge reduces stalls", "transport X is better", or "cache Y writes less" can be tested against a stable baseline.

## 2. Source-derived constraints

M0 inherits the current product/architecture constraints:

- Android phones/tablets first.
- Long-form VOD only.
- Network instability and loss are normal operating conditions.
- No Shorts.
- No Live.
- No TV/iOS implementation.
- No YouTube extractor in M0.
- No hidden VPN bypass.
- Performance claims remain Provisional until repeatable evidence exists.

## 3. Research conclusions adopted for M0

### 3.1 Android/API baseline

Use:

```text
compileSdk = 36
targetSdk  = 36
minSdk     = 23   # provisional
```

Rationale:

- Google Play requires new phone/tablet apps and updates to target API 36 from 2026-08-31.
- Media3 core video/DASH supports API 23+.
- AndroidX's current default minSdk is 23.
- The product is explicitly relevant to older/less capable Android devices, so increasing minSdk without evidence would reduce useful coverage.
- Android 17/API 37 is tested as compatibility input, not used as the production target while the current SDK remains in preview status.

The minSdk is **Provisional**. It is a compatibility boundary, not an architecture invariant.

### 3.2 Build toolchain

Initial pinned baseline:

```text
JDK        17
AGP        9.4.0
Gradle     9.6.0
BuildTools 36.0.0
```

Use AGP built-in Kotlin for Android modules.

Do not apply `org.jetbrains.kotlin.android` to Android modules in M0. AGP 9.x enables built-in Kotlin by default.

Do not force a newer standalone KGP into Android modules only to chase the latest Kotlin language version. AGP 9.4 ships a known built-in Kotlin integration; toolchain stability is more important in M0 than language novelty.

A standalone host-side tool may use Java 17 to avoid adding a second Kotlin Gradle toolchain before it is needed.

### 3.3 Stable Android libraries

Initial stable dependencies:

```text
Compose BOM  2026.06.00
Media3       1.11.1
Benchmark    1.5.0
Activity     1.13.0
Lifecycle    2.11.0 only if a state holder requires it
```

Use stable releases. Preview libraries require a specific, documented need.

### 3.4 Network stack

M0 corrects the earlier "Cronet vs OkHttp" framing.

Media3 currently recommends `HttpEngine` as the default network stack on API 34+ (or relevant SDK extension), with HTTP/3/QUIC support. M0 therefore defines a transport seam but does **not** select a universal winner.

Initial transport policy:

```text
API 34+:
  HttpEngine candidate / preferred platform path

Older API:
  DefaultHttpDataSource portable fallback

M2:
  evaluate whether OkHttp, GMS Cronet or Embedded Cronet adds enough value
  for the actual SpongeTube population/workload
```

Do not add Embedded Cronet merely to obtain HTTP/3 on old devices; its APK/runtime cost must be justified by evidence.

Use one shared network-engine/client instance per backend when that backend is active.

### 3.5 Modularity

Do not copy a large "Clean Architecture" module graph before the code exists.

Official Android guidance allows small applications to keep layers in packages/modules as appropriate, and official modularization guidance notes the cost of excessive granularity. Community experience from Android projects repeatedly reports similar friction from premature module splitting.

M0 uses only boundaries with an immediate test/build purpose.

### 3.6 Performance measurement

Emulators are suitable for:

- deterministic correctness;
- API compatibility;
- failure injection;
- repeatable functional scenarios.

M0 is explicitly emulator-only.

Macrobenchmark/emulator timings are retained as diagnostic observations, but M0 does not produce or validate representative end-user performance conclusions. Physical-device performance validation starts in the later performance/hardening milestone and is not an M0 exit criterion.

### 3.7 Baseline Profiles

Create the benchmark foundation in M0, but do not optimize the empty bootstrap app with a Baseline Profile.

A Baseline Profile is meaningful when real critical user journeys exist. Profile generation/optimization becomes relevant when the product player/navigation flow exists.

## 5. Build system design

### 5.1 Kotlin DSL and version catalog

Use:

- `settings.gradle.kts`
- `build.gradle.kts`
- one `gradle/libs.versions.toml`

Repository declarations live in settings and project repositories are rejected.

No dynamic versions such as `1.+`, `latest.release` or `SNAPSHOT` are allowed for production dependencies.

### 5.2 build-logic

Use an included `build-logic` build rather than `buildSrc`.

Create only conventions actually shared by multiple modules, initially approximately:

```text
spongetube.android.application
spongetube.android.library
spongetube.android.test
```

One-off configuration stays in the owning module.

Do not create a plugin for every Gradle block.

### 5.3 Gradle execution

Enable and test from the beginning:

- configuration cache;
- build cache;
- parallel execution where compatible.

Configuration-cache failures are treated as build defects, not permanently suppressed.

The build must work from the Gradle Wrapper.

### 5.4 Supply-chain baseline

M0 establishes:

- Gradle Wrapper validation in CI;
- pinned dependency versions;
- Gradle dependency verification with SHA-256 metadata;
- review of dependency-verification updates;
- full commit SHA pinning for third-party GitHub Actions.

Do not add blanket dependency locking while all direct dependencies are exact and changing/dynamic versions are prohibited. Introduce locking when a real resolution case requires it; dependency verification is mandatory regardless.

## 7. M0-B — Deterministic Media Lab (#5)

Detailed implementation plan: `.work/milestones/M0-B.md`.

### Goal

Remove live YouTube/CDN variability from correctness and performance experiments.

### Host server

Implement a dependency-light Java 17 host tool using the JDK HTTP server or equivalent standard-library primitives unless implementation proves them insufficient.

Requirements:

- bind two independent listeners to IPv4 loopback only: data (`/fixtures/...`) and host-only control (`/__lab/...`);
- use independent bounded executors so a deliberate media no-progress window cannot starve health/config scheduling;
- Android emulator and physical devices reach only the data listener through `adb reverse` and an app-side localhost endpoint;
- explicitly record that `adb reverse` is not valid evidence for VPN/default-route semantics;
- cleartext HTTP is enabled only in the lab/debug configuration for localhost and must not weaken production network security policy;
- HTTP Range support with deterministic single-range semantics;
- static DASH/fMP4 serving;
- progressive MP4 serving;
- deterministic application-layer response pacing;
- deterministic first-body delay;
- deterministic session-wide no-progress window;
- explicit documentation that these are application-layer impairment profiles, not a faithful TCP/QUIC/packet-loss/VPN simulator;
- structured JSONL request log plus B2 session-event trace;
- lab-only response correlation headers for session/request/profile/plane and later scenario hash;
- canonical resolved scenario identity/hash in B2;
- clean shutdown and partial-bind cleanup.

M0 does **not** need to simulate the full YouTube/SABR protocol.

### Fixtures

Fixtures must be synthetic or otherwise redistributable with explicit provenance.

Initial fixture set:

#### F0 — Progressive smoke

Small progressive MP4 for basic Range/read/seek validation.

#### F1 — Long-form separate A/V

Several-minute synthetic VOD with:

- separate video and audio tracks;
- AVC video;
- AAC audio;
- fMP4/DASH;
- enough duration to exercise a long outage.

The source may be a generated test pattern + generated tone.

Store fixture id, duration, codec/container, nominal bitrate, actual byte size, measured average bitrate, segment/range size distribution where applicable, generator version, generation command/manifest, SHA-256 and license/provenance.

For F1, fixture-change evidence has three levels: SHA-256 byte identity, structural inspection (ffprobe), and DASH/CMAF conformance validation. Heavy conformance does not rerun on ordinary PRs when fixture bytes/MPD are unchanged.

F1 should expose exactly one selected video representation and one selected audio representation in M0 so adaptive representation choice cannot add benchmark variance.

Keep fixtures small enough for ordinary Git. Do not introduce Git LFS in M0 unless fixture size proves it necessary.

### Network profiles implemented in M0

M0 only needs the profiles required to prove the harness:

```text
N0 GOOD
N1 SLOW
N4 LONG_OUTAGE
```

Recommended deterministic fixtures:

```text
N0: CONTROL — no artificial first-body delay, unlimited application-body rate, no no-progress window
N1: aggregate fixture-body pacing at 0.50 × F1 actual reference playback bitrate, with 120 ms configured first-body delay (not RTT)
N4: healthy period followed by a deterministic 120 s **session-wide fixture-body no-progress window**, then normal delivery resumes
```

The exact implementation can compress the long scenario for PR smoke tests, but the canonical N4 acceptance run remains 120 seconds.

N2/N3/N5–N11 remain specified by `.work/VERIFICATION.md` and are implemented in M2 unless M0 needs a primitive earlier.

M0 does not claim to emulate RTT, packet loss, congestion control, route replacement, VPN failure or QUIC connection migration merely by delaying application bytes. Those transport/network semantics belong to M2.

The JDK Media Lab is intentionally sufficient for deterministic HTTP/1.1 test delivery. It therefore cannot be used to prove HTTP/3/QUIC performance or connection-migration claims for HttpEngine.

### Request/session evidence

Each completed request produces a versioned JSONL row with session/request/fixture/resource/profile identity, raw/resolved Range, status, planned/body-written bytes, same-clock timings, configured rate/no-progress values and explicit outcome.

B2 also emits session-level transitions (rate resolution, first media progress, no-progress enter/exit) and a canonical `ResolvedScenario` with SHA-256 `scenarioHash`.

Android and host clocks remain separate domains. Cross-domain joining uses session/request/scenario/fixture identity and lab response headers, never raw timestamp subtraction.

Logs must not contain user credentials because the lab has none.

Range behavior is part of the Media Lab correctness contract and must cover at least valid single-range `206`, `Content-Range`, `Content-Length`, `Accept-Ranges`, open-ended/suffix cases used by the client, and invalid/unsatisfiable `416` behavior. Multi-range responses are not required in M0.

## 9. M0-D — Measurement & Impairment Harness (#7)

### Goal

Create measurements that are stable enough to compare later M1/M4 behavior.

### App-side event model

Record events using monotonic time.

Initial events:

```text
SESSION_STARTED
PLAY_REQUESTED
PLAY_INTENT_CHANGED
PREPARE_STARTED
PLAYBACK_READY
FIRST_FRAME
BUFFERING_STARTED(reason = STARTUP | REBUFFER | SEEK)
BUFFERING_ENDED(reason = STARTUP | REBUFFER | SEEK)
SEEK_STARTED
SEEK_COMPLETED
FIRST_FRAME_AFTER_SEEK
PLAYBACK_ENDED
PLAYBACK_ERROR
SESSION_ENDED
```

Use structured records rather than parsing human logcat text.

### Derived playback metrics

M0 computes:

```text
TTFF_MS
STALL_COUNT
STALL_TOTAL_MS
REBUFFER_RATIO
PROGRESS_INTENT_WALL_MS
SEEK_TO_FRAME_MS
SESSION_WALL_MS
```

Metric definitions are normative:

```text
TTFF_MS =
  FIRST_FRAME - PLAY_REQUESTED

STALL_COUNT =
  count(REBUFFER intervals after FIRST_FRAME
        while playback is intended to progress
        and no seek is active)

STALL_TOTAL_MS =
  sum(duration of closed qualifying REBUFFER intervals)

PROGRESS_INTENT_WALL_MS =
  sum(wall-clock intervals after FIRST_FRAME
      while playIntent=true
      and no seek is active
      and playback has not terminated)

REBUFFER_RATIO =
  STALL_TOTAL_MS / PROGRESS_INTENT_WALL_MS
  when PROGRESS_INTENT_WALL_MS > 0, otherwise null

SESSION_WALL_MS =
  SESSION_ENDED - SESSION_STARTED

SEEK_TO_FRAME_MS =
  FIRST_FRAME_AFTER_SEEK - SEEK_STARTED
```

Initial startup buffering is not counted as a rebuffer stall; its cost is represented by TTFF. Seek-induced buffering is not counted as a normal playback stall. Paused time is excluded through PLAY_INTENT_CHANGED. PROGRESS_INTENT_WALL_MS is deliberately a wall-clock denominator, not claimed media-timeline progress. An unclosed REBUFFER makes the derivation PARTIAL rather than being silently repaired.

### Network and lab metrics

Combine app session/request identity with Media Lab request/session traces:

```text
REQUEST_COUNT
NETWORK_BYTES
UNIQUE_RANGE_BYTES
DUPLICATE_RANGE_BYTES
HTTP_ERROR_COUNT
FETCH_AMPLIFICATION

LAB_RATE_ERROR_PCT
LAB_FIRST_BODY_DELAY_ERROR_MS
LAB_NO_PROGRESS_DURATION_ERROR_MS
LAB_MAX_SCHEDULER_SLIP_MS
```

These definitions become reusable for Sponge Core later.

Duplicate bytes are calculated by media resource/range coverage, not merely by repeated URLs:

```text
DUPLICATE_RANGE_BYTES =
  total bytes served
  - size(union(served byte intervals))
```

for each logical byte-addressable resource, then summed for the scenario.

Android and host Media Lab monotonic timestamps are separate clock domains. Durations are computed only within one clock domain. Cross-process correlation uses session/request ids and resource/range identity; raw host/device timestamps must not be subtracted from each other unless an explicit clock-synchronization method is introduced.

### Storage metrics

For Baseline B:

```text
CACHE_BYTES_AT_START
CACHE_BYTES_AT_END
CACHE_HIT/READ observations where Media3 exposes reliable data
```

Do not invent a metric if Media3 does not expose it reliably; record a limitation instead.

### Trace instrumentation

Add named Perfetto/system trace events around important lab operations.

Use a dedicated release-like, non-debuggable/profileable benchmark build variant so A/B comparisons use the same production-like compilation state.

Macrobenchmark records the compilation/startup mode as part of run identity. A/B comparisons use the same compilation state unless compilation is the experimental variable.

Use Macrobenchmark 1.5.0 to collect:

- application startup metrics where relevant;
- frame metrics for lab UI only where useful;
- custom trace sections for app-defined operations;
- JSON and Perfetto trace output.

M0-D adds a versioned Perfetto TraceSummary specification for stable machine-readable CPU/memory/I/O/custom-section extraction where supported. Raw traces remain the root-cause artifact.

Media-specific TTFF/stall correctness remains defined by the app event schema and server trace, not by a misleading generic app-startup metric.

### Run manifest and result schema

Each automated run first emits a versioned `run-manifest.json` tying together:

- runId / commit / build variant;
- fixture id + manifest hash;
- scenario id + scenario hash;
- baseline mode;
- transport;
- cache state;
- device/runtime/compilation state;
- fixed run-order seed.

`result.json` then records metrics/errors and references raw server/app/Perfetto/calibration artifacts. Identity is not duplicated: the manifest is the sole build/device/baseline identity source, and result v1 binds to it with `manifestSha256` plus run/session/scenario identity.

The committed schemas are stable enough for CI comparison; adding optional fields is backward-compatible within schema version 1.

## 10. M0-E — CI, Testing & Supply Chain (#8)

### Goal

Fast pre-merge feedback, deterministic artifacts and conservative permissions.

### Stable PR checks

Create stable required-check names:

```text
verify
android-smoke
```

The executable repository contract is the stable job names `verify` and `android-smoke`. Both must be green and repeatable before M0 closes. Repository-admin ruleset enforcement should reference exactly these names when administration access is available; ruleset mutation itself is not an executable correctness artifact and is not an M0 blocker.

### verify

Runs on every PR:

- checkout;
- JDK 17;
- Gradle setup;
- wrapper validation;
- build-logic checks;
- dependency verification;
- lint;
- local/unit/component tests;
- assemble debug lab build;
- configuration-cache compatible invocation.

GitHub workflow permissions are read-only by default:

```yaml
permissions:
  contents: read
```

Increase permission only in a separate job with a documented need.

### Gradle Action

Use `gradle/actions/setup-gradle` v6 pinned to a full commit SHA. Use its built-in wrapper validation rather than adding a redundant separate wrapper-validation Action unless a concrete need emerges.

Choose `cache-provider: basic` for M0 as a transparent open-source policy baseline, not because it has been measured faster. If CI cache behavior becomes a problem, compare alternatives with evidence. Do not layer `setup-java cache: gradle` or a second Gradle User Home cache on top of it.

All PR workflows use `concurrency` with cancellation of superseded runs and finite per-job timeouts. Checkout jobs that do not push set `persist-credentials: false`.

The default behavior where feature/PR branches read cache while only the default branch writes cache is desirable.

### android-smoke

Use an Android emulator/device automation path for correctness, initially on API 36.

Requirements:

- boot/install lab app;
- start Media Lab;
- run a short deterministic N0 scenario;
- run a short N1 smoke scenario;
- publish JUnit/result artifacts.

Add API 23 minimum compatibility and API 34 transport-boundary coverage to periodic execution rather than making every PR pay for the complete device matrix.

M0 standardizes one emulator mechanism: explicit Android SDK system-image/AVD creation plus `adb` orchestration on the pinned Ubuntu runner. This path already proved boot, `adb reverse`, Media Lab lifecycle, Macrobenchmark and artifact export during M0-D. Gradle Managed Devices are not carried as a second stack. Revisit the choice only if measured flakiness or maintenance cost appears.

### Nightly

Nightly may run:

- API 23 minimum-compatibility coverage;
- API 34 HttpEngine boundary coverage;
- API 36 target coverage;
- optional API 37 compatibility smoke;
- canonical N4 120-second outage;
- more iterations;
- Macrobenchmark trace capture.

Do not make API 37 preview compatibility a required PR gate.

### Artifacts

On failure and benchmark jobs, retain:

- test reports;
- structured scenario result JSON;
- Media Lab JSONL request trace;
- Perfetto traces where generated;
- lint reports.

Do not commit raw multi-megabyte traces into Git.

### Dependabot

Once Gradle and Actions dependencies exist:

- enable security alerts/updates;
- configure reviewed Gradle and GitHub Actions version-update PRs;
- group routine non-security updates where practical;
- never auto-merge dependency upgrades.

### CodeQL

CodeQL is optional in M0. Do not delay the media/test foundation solely to add another long-running security job. Add it when its signal/cost is understood.

## 11. M0-F — Acceptance Evidence (#9)

### Goal

Close M0 with evidence, not with "it builds on my machine".

### Harness calibration

Before comparing players, validate the harness itself:

- N1's resolved aggregate rate is 0.50 × committed F1 reference playback bitrate;
- observed rate, first-body delay and N4 duration are compared with configured values;
- scheduler slip/error distributions are retained;
- Range accounting and request trace totals agree with known fixture sizes/ranges;
- host real-socket calibration characterizes bounded bytes that may drain from already-written socket/kernel buffers after the server enters a no-write window.

Do not invent a permanent ±X% threshold before pilot runs characterize host/runner variance. The first evidence reports raw calibration error; a gate is added only after that evidence.

### Acceptance matrix

At minimum run Baselines A and B for:

```text
F1 × N0
F1 × N1
F1 × N4
```

Capture TTFF, stalls, stall duration, requests, network bytes, duplicate ranges where measurable, cache size for B, explicit cache state (`NONE` / `COLD` / `WARM`), errors and trace/artifact references.

Use one committed deterministic case order for M0 correctness acceptance. The order seed remains part of run identity, but M0 does not use ordering to support a performance inference. Interleaved/block-randomized performance protocols move to later representative-device work where distributions are actually compared.

Preserve all raw observations. M0 reports every observed value directly and does not compute p95, effect-size, thermal or uncertainty claims from emulator data. Distributional statistics and repetition-count design begin only when a later milestone performs representative performance experiments.

Do not silently discard outliers. A run may be marked invalid only for a predeclared reason, and its artifact remains retained.

### Emulator-only M0 acceptance rule

M0-F runs on a deterministic API 36 emulator and validates correctness, reproducibility, cache-state identity and evidence integrity only.

Record:
- API/system-image fingerprint and ABI;
- exact build commit and compilation/startup mode;
- fixture/scenario hashes;
- baseline mode and observed cache bytes;
- raw playback/network/calibration artifacts.

Timing/resource observations remain diagnostic and non-representative. M0 does not compute or promote p95, effect-size, thermal, battery, codec-device or hardware-performance conclusions.

Physical-device benchmarking remains required before a later milestone validates representative device performance, but it is not carried as unfinished M0 work.

### Evidence file

Commit:

`.work/evidence/YYYY-MM-DD-m0-baseline.md`

The evidence record must distinguish:

- Correctness conclusions.
- Performance observations.
- Unvalidated hypotheses.
- Known measurement limitations.

M0 does not need SpongeTube to outperform anything. It needs trustworthy baselines.

## 12. Test strategy

Apply the lowest-fidelity test that can prove the behavior.

### Host/local tests — every PR

Use for fixture manifest/checksum logic, scenario state machines, result schema, metric derivation, Range parsing and Media Lab pacing/control logic.

### Android component/integration — every PR

Use for Media3 DataSource integration, playback event adapter, SimpleCache behavior, basic seek and app/lab wiring.

### Emulator application smoke — every PR

Run only a small number of representative scenarios.

### Wider emulator matrix — nightly

Use for API/runtime compatibility and deterministic failure scenarios.

### Physical device — evidence/release cadence

Use for actual performance, codec/device behavior, thermal/power observations.

Media applications are hardware-sensitive; do not replace physical testing with an ever-larger emulator matrix.

## 13. UX rule for M0

M0's screen is a lab surface, not a prototype of the final Home/player product.

It must:

- be usable with one hand;
- clearly show selected fixture/profile/baseline;

Product UX work begins after the core measurement path is trustworthy.
