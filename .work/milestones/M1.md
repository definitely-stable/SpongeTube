# SpongeTube M1 — Persistent Playback Core

Status: **Implementation contract**
Date: **2026-09-23**
Parent roadmap: \`.work/ROADMAP.md\`
Architecture authority: \`.work/ARCHITECTURE.md\`
Verification authority: \`.work/VERIFICATION.md\`

## 1. Goal

Prove the smallest Sponge-owned playback core that can:

\`\`\`text
one remote owner fetch
  -> crash-consistent immutable extent
  -> committed metadata publication
  -> required-track playable coverage
  -> Media3 playback
\`\`\`

M1 exists to prove durable reserve correctness and recovery before YouTube/provider complexity or adaptive Smart Buffer policy is introduced.

## 2. M0 evidence that constrains M1

M0 established the reproducible Android/media laboratory and exposed four implementation-relevant facts:

1. Standard Media3 warm cache reduced network demand but did not turn a long N4 outage into successful continuous playback.
2. The observed N4 warm failure boundary moved by about one media-segment horizon when common audio/video retained coverage increased. This is evidence that playable required-track coverage is more useful than raw retained bytes.
3. M0 cache observation could under-report partial data before player/cache release while the immediately following warm case observed additional retained bytes. M1 therefore requires explicit receiving/commit/publication semantics.
4. N4 generated duplicate range bytes/retry churn even without HTTP status errors. M1 therefore needs explicit fetch ownership and outcome accounting.

M0 remains closed. These observations are a handoff into M1, not a reason to reopen M0.

## 3. Scope

M1 MUST implement:

- provider-independent \`MediaAsset\`, \`TrackVariant\`, \`FetchUnit\` identities sufficient for the deterministic fixture;
- immutable durable \`ExtentStore\`;
- metadata persistence and startup recovery;
- \`CoverageIndex\`;
- exact \`PlayableCoverage\` and \`DurablePlayableReserve\`;
- deterministic fixed coverage seed builder + independent verifier;
- \`FetchBroker\` with single-flight ownership;
- minimal priority escalation for playback urgency;
- \`PlaybackBridge\` to Media3;
- process-death/crash-point verification;
- N4 recovery scenarios;
- machine-readable evidence required by this milestone.

M1 MAY implement only the smallest helper abstractions necessary to satisfy these contracts.

## 4. Explicit non-goals

M1 does not attempt to solve:

- adaptive reserve target selection / Smart Buffer;
- battery, thermal, dwell or metered policy optimization;
- VPN/default-route transition policy;
- DNS/TLS/loss/jitter network fault matrix;
- provider 403/429/descriptor refresh;
- YouTube extraction;
- transport winner selection;
- packed extent containers;
- sophisticated production GC/compaction;
- Android background Keep Offline scheduling;
- physical-device performance claims.

Those remain M2/M3/M4/M6/M8 work unless a concrete M1 correctness blocker requires a small prerequisite.

## 5. Normative identities

### 5.1 Media identity

A provider URL is never storage identity.

At minimum the deterministic M1 fixture resolves stable:

\`\`\`text
MediaAssetId
TrackId
RepresentationId
FetchKey
ExtentId
\`\`\`

A \`FetchKey\` identifies the exact retrievable coverage/resource identity used for single-flight ownership. URL rotation must not redefine already committed media identity.

### 5.2 Playback requirement set

A playback plan explicitly names every representation/component required for playable output. Core coverage semantics do not assume that all providers expose exactly one separate video representation plus one separate audio representation.

\`\`\`text
PlaybackRequirementSet
  = exact requirements of the selected PlaybackPlan
\`\`\`

For the canonical F1 fixture:

\`\`\`text
required = VIDEO representation R1 + AUDIO representation R1
\`\`\`

CoverageIndex computes the intersection of the exact requirement set. A future muxed/interleaved provider representation may therefore use a different requirement set without changing interval algebra. Captions are not a required playback component in M1.

## 6. Coverage contract

For each required track:

\`\`\`text
TrackCoverage(track)
  = union(media intervals from PUBLISHED + VALID extents
          matching the exact track/representation identity)
\`\`\`

Then:

\`\`\`text
PlayableCoverage
  = intersection(Coverage(each required playback requirement))
\`\`\`

For current playhead \`P\`:

\`\`\`text
DurablePlayableReserve(P)
  = duration of the maximal contiguous interval [P, E)
    contained in PlayableCoverage
\`\`\`

Consequences:

- coverage islands after a hole do not increase current reserve;
- for the canonical F1 split-A/V fixture, video-only or audio-only bytes never imply playable reserve;
- different quality representations are not merged;
- missing required init/index dependency prevents dependent media from being considered playable;
- partial/truncated data contributes only independently proven usable coverage, otherwise zero;
- seeks use resolved timeline/range mappings;
- raw byte count or nominal bitrate division is not a coverage oracle.

### 6.1 Separate observables

Evidence keeps these distinct:

\`\`\`text
networkBytesReceived
receivingBytes
sealedBytes
verifiedBytes
durableBytes
publishedCoverage
DurablePlayableReserve
PlayerBufferedAhead
\`\`\`

\`PlayerBufferedAhead\` is not durable reserve.

### 6.2 CoverageIndex invariant

CoverageIndex may expose only metadata already committed as \`PUBLISHED + VALID\`.

Every canonical runtime snapshot must be reproducible by an independent post-run verifier reading committed metadata plus immutable extent files.

If runtime and independent interval sets disagree, the run fails.

## 7. Extent lifecycle and crash consistency

Normative lifecycle:

\`\`\`text
RECEIVING
   -> SEALED
   -> VERIFIED
   -> DURABLE
   -> PUBLISHED
\`\`\`

### RECEIVING

- unique temporary file under the same filesystem as the final extent;
- active writer may append;
- never contributes coverage.

### SEALED

- writer closed;
- attempt identity, expected byte range and final received length stop changing;
- still contributes zero coverage.

### VERIFIED

- immutable length and SHA-256 integrity validated;
- representation/resource identity validated;
- still contributes zero coverage.

### DURABLE

- same-filesystem atomic rename completed to immutable final path;
- file durability barrier performed where available;
- still contributes zero coverage until metadata publish.

### PUBLISHED

- Room/SQLite metadata transaction commits extent identity, location, length, SHA-256, media interval, representation identity and \`VALID\` state;
- only now may CoverageIndex expose it.

### 7.1 Crash matrix

| Crash point | Required restart behavior |
| --- | --- |
| during receive | no coverage; incomplete temp cleaned or retained only by explicit future policy |
| after seal | no coverage |
| after verification | no coverage |
| after final rename, before metadata publish | orphan file, no coverage |
| during DB transaction | atomic rollback or commit |
| after publish | immutable file must exist and validate |

M1 recovery MUST NOT automatically adopt orphan immutable files. It may delete them after validation/age policy. Adoption is deferred because it creates another publication path that M1 does not need.

A published row pointing at a missing, truncated or digest-invalid file is quarantined/invalidated before it can be exposed as playable coverage.


### 7.2 Metadata persistence implementation

ADR-0001 selects **Room 3.0.3** over **AndroidX SQLite 2.7.1 used directly** for M1 metadata, with **AndroidSQLiteDriver** as the initial driver.

The architectural invariant remains SQLite transactions plus media bytes outside the database. Room is the implementation layer, not the source of truth for media payload bytes.

M1-B adoption rules:

- add Room/KSP only in the storage-owning module when the first real schema/entities are introduced;
- retain AGP built-in Kotlin; do not reintroduce a separate Kotlin Android plugin merely for Room;
- use Room's SQLiteDriver-based APIs, not legacy SupportSQLite compatibility APIs;
- use the platform AndroidSQLiteDriver initially rather than BundledSQLiteDriver; bundle a separate SQLite engine only after a measured/correctness need exists;
- export generated Room schemas and commit them for migration/schema review;
- keep DAO/database APIs internal to the storage subsystem so Room is not leaked into Sponge Core contracts.

Room 3.0.3 is selected because M1 benefits from compile-time query/schema checking, explicit migrations and coroutine-native transaction APIs. The lower-level AndroidX SQLite path remains a fallback if M1-B exposes a concrete correctness, compatibility or build-system blocker.

No Room/KSP runtime dependency is added by M1-A; the dependency enters with M1-B implementation.

## 8. Partial HTTP response / continuation contract

M1 deterministic origin supports range-based continuation tests.

Resume/append is allowed only when all identity and range invariants match.

Minimum checks:

- same MediaAsset/Track/Representation resource identity;
- expected total length remains compatible;
- returned start offset equals expected continuation;
- returned range metadata is internally consistent;
- validator identity, when present, is unchanged;
- a full-body response to a continuation request is never blindly appended;
- impossible/mismatched ranges are classified as failed attempts;
- partial bytes remain unpublished until the normal extent commit barrier completes.

Provider-specific URL expiry and descriptor refresh are not M1 concerns.

M1 requires continuation correctness within an active attempt. Persisting unfinished attempts across process death is not an M1 exit criterion; later provider/network-resilience work may add it only when the chosen delivery path has a stable continuation identity.

## 9. Fixed coverage seed protocol

Canonical positive targets:

\`\`\`text
S0
S10
S30
S60
S120
\`\`\`

The number is semantic target playable time from media origin, not megabytes and not a provider-segment count.

The seed builder:

1. resolves the canonical F1 track timeline;
2. selects complete required-track units necessary to reach the target;
3. writes them through the same ExtentStore publication contract or an explicitly equivalent deterministic seed import path;
4. records exact immutable extent identities;
5. invokes an independent verifier before playback begins.

Canonical negative/boundary seeds:

\`\`\`text
S30_VIDEO_HOLE
S30_AUDIO_HOLE
S30_MISSING_INIT
S30_PARTIAL_TAIL
S30_WRONG_REPRESENTATION
\`\`\`

A negative seed passes when runtime coverage remains conservative and matches independent reconstruction.

## 10. FetchBroker contract

One \`FetchKey\` has at most one physical origin owner fetch at a time.

Multiple consumers may join:

\`\`\`text
SharedFetch
  <- playback consumer
  <- reserve consumer
  <- durable writer
\`\`\`

Rules:

- joining never starts a second owner request for the same active FetchKey;
- cancellation is reference-counted;
- cancelling one consumer does not cancel work still needed by another;
- playback urgency may raise existing work priority;
- priority escalation does not cancel/restart the same work;
- network bytes, unique range bytes and duplicate range bytes remain observable;
- fetch outcome is richer than HTTP status and includes transport timeout/cancellation/range rejection/storage failure.

M1 request-budget logic is intentionally minimal: it prevents unbounded retry loops and records attempts. Adaptive provider-specific retry policy belongs to M2.

## 11. PlaybackBridge contract

Media3 remains decoder/player owner but not independent remote media-fetch owner for Sponge-managed coverage.

Read path:

\`\`\`text
Media3 read/seek
    -> PlaybackBridge
       -> CoverageIndex
          -> local published extent
          OR
       -> FetchBroker for missing coverage
\`\`\`

MUST:

- read locally when requested coverage is published;
- route remote misses through FetchBroker;
- join matching in-flight work;
- never install a second hidden upstream path that bypasses FetchBroker for the same media;
- support cached seek;
- preserve one player/session across N4 restoration where normal Media3 recovery permits.

## 12. Minimal scheduler scope

M1 only needs two urgency classes:

\`\`\`text
PLAYBACK_CRITICAL
RESERVE
\`\`\`

It must support deterministic ordering and priority escalation of an existing shared fetch.

Full DeadlineScheduler optimization based on estimated fetch time, stall probability, user mode, resource constraints and adaptive reserve targets is deferred to M4.

## 13. N4 recovery contract

M0 N4 measured a fixed no-progress outage. M1 uses recovery-capable variants.

### N4R-SHORT — outage shorter than reserve

Start from a verified fixed seed whose durable reserve exceeds the outage.

Pass:

- no reserve-exhaustion playback stall;
- no coverage loss/corruption;
- no duplicate independent owner fetch;
- network restoration does not trigger refetch of already valid coverage.

### N4R-EXHAUST — outage longer than reserve

Pass:

- runtime does not overstate reserve;
- eventual stall is permitted after durable reserve and already-held player buffer are exhausted;
- retries remain bounded and observable;
- existing committed coverage stays valid.

No exact wall-clock stall threshold is a correctness requirement because player-internal buffering is separate from durable reserve.

### N4R-RESTORE — restore during stall

Pass:

- missing work proceeds again after origin restoration;
- already valid coverage is not redundantly fetched;
- newly received bytes appear in coverage only after durable publish;
- playback resumes without replacing the entire session merely to reset state;
- no corruption/overlap ambiguity is introduced.

### N4R-FLAP

SHOULD in M1:

- repeated no-progress/restoration cycles;
- stable final coverage;
- bounded request attempts;
- no overlapping owner-fetch storm.

## 14. Evidence contract

Canonical M1 evidence contains:

- run manifest;
- seed manifest and pre-playback verification result;
- ordered extent lifecycle events for diagnostics;
- committed SQLite extent metadata snapshot used by the independent oracle;
- independently verified immutable-file snapshot (existence, length, SHA-256, path);
- ordered fetch ownership/consumer/outcome events;
- periodic/event-driven coverage snapshots;
- player state/stall timeline;
- configured and observed N4 gate markers;
- restart/recovery summary;
- independent post-run coverage reconstruction from committed metadata + verified files;
- origin request trace and unique/duplicate range summary.

Runtime-generated coverage alone can never be the acceptance oracle.

The independent M1 host oracle lives in `scripts/measurement/m1_oracle.py`. Before M1-C acceptance, it must be executable against real artifacts and paired with a host filesystem verifier that independently stats and SHA-256 hashes immutable extent files from the storage root. It must not treat caller-supplied repetitions of database length/digest values as file verification.

The oracle reconstructs published interval sets from the committed SQLite metadata snapshot plus `verified-extent-files-v1`; it does not consume runtime CoverageIndex output or lifecycle `PUBLISHED` events as authority. A `PUBLISHED` event without a committed metadata row contributes zero coverage. Canonical acceptance compares runtime and oracle interval/reserve outputs exactly.

Schemas live under `.work/schemas/`, with representative examples under `.work/schemas/examples/m1/`. `scripts/measurement/tests/test_m1_contracts.py` validates the repository-supported JSON-Schema subset and independent interval/oracle semantics on every `Verify` run.

## 16. CI policy

Ordinary M1 PRs should run fast deterministic host/unit/state-machine verification and only targeted emulator smoke where Android integration changed.

The full canonical M1 emulator matrix belongs to M1-F/M1-G and explicit evidence runs.

API compatibility matrix remains periodic plus targeted compatibility-relevant PR execution; it is not a substitute for M1 semantic correctness tests.

## 17. Exit

M1 is complete only when all are true:

- one remote owner fetch per active FetchKey is proven under overlapping consumers;
- partial/uncommitted/corrupt/missing files never produce playable coverage;
- fixed positive and negative seeds are independently verified;
- DurablePlayableReserve is contiguous from playhead and required-track conservative;
- cached seek needs no remote request;
- process death preserves valid published coverage without creating phantom coverage;
- N4R-SHORT is survived when durable reserve covers the outage;
- N4R-EXHAUST does not hide exhaustion by inflated coverage;
- N4R-RESTORE resumes through the same ownership/storage path after connectivity returns;
- canonical runtime coverage snapshots equal independent reconstructed interval sets;
- evidence makes no representative performance claim from emulator timing.
